# План проверки согласованности документации

**Дата:** 2025-10-20  
**Цель:** Проверить согласованность всей документации с помощью системы тегов

---

## 🎯 Задачи проверки

### 1. Структура проекта
- Проверить что все пути в `#structure:path` существуют в PROJECT_STRUCTURE.md
- Проверить что все деревья `#structure:tree` соответствуют реальной структуре
- Проверить что импорты/экспорты указывают на существующие файлы

### 2. Архитектурные правила (DDD + Clean Architecture)
- Проверить что Domain не импортирует из других слоев
- Проверить что Presentation не импортирует Application/Infrastructure напрямую
- Проверить что Infrastructure не зависит от Application
- Проверить что все импорты через Public API (index.ts)

### 3. Сущности (классы, интерфейсы, типы)
- Проверить что все `#class:` теги согласованы между файлами
- Проверить что все `#interface:` теги согласованы
- Проверить что типы используются последовательно
- Проверить что нет противоречий в определениях

### 4. API контракты
- Проверить что все `#api:` endpoints согласованы
- Проверить что DTO соответствуют API контрактам
- Проверить что типы запросов/ответов согласованы

---

## 📊 Этапы проверки

### Этап 1: Структура (2-3 часа)
**Источник истины:** `docs/PROJECT_STRUCTURE.md`

**Действия:**
1. Извлечь все `#structure:path` теги из документации
2. Извлечь структуру из PROJECT_STRUCTURE.md
3. Сравнить пути с описанной структурой
4. Найти несоответствия
5. Создать отчет с рекомендациями

**Команды:**
```bash
# Найти все пути в тегах
grep -rh "#structure:path" docs/ steps/ | grep -o "// src/[^\"]*" | sort -u

# Найти все импорты
grep -rh "^import.*from '@/" docs/ steps/ | sort -u
```

**Выходной файл:** `.docs-meta/CONSISTENCY_STRUCTURE.md`

---

### Этап 2: Архитектурные границы (2-3 часа)
**Источник истины:** `docs/ARCHITECTURE_BOUNDARIES.md`

**Действия:**
1. Извлечь все импорты из примеров кода
2. Проверить что Domain не импортирует Application/Infrastructure/Presentation
3. Проверить что Presentation не импортирует Application/Infrastructure напрямую
4. Проверить что все импорты через Public API
5. Найти нарушения архитектурных правил

**Правила для проверки:**
- Domain → ТОЛЬКО Domain
- Application → Domain (через Public API)
- Infrastructure → Domain интерфейсы (через Public API)
- Composition → ВСЁ (единственный слой)
- Presentation → Domain типы + Composition facades (через Public API)

**Команды:**
```bash
# Найти импорты в Domain
grep -rh "import.*from '@/" docs/ steps/ | grep -i "domain" | grep -v "from '@/domain'"

# Найти прямые импорты в Presentation
grep -rh "import.*from '@/application\|@/infrastructure'" docs/ steps/
```

**Выходной файл:** `.docs-meta/CONSISTENCY_ARCHITECTURE.md`

---

### Этап 3: Сущности (3-4 часа)
**Источники истины:** 
- `docs/contracts/domain-types.md`
- `docs/contracts/system-interfaces.md`
- `docs/TYPES_AND_ENTITIES.md`

**Действия:**
1. Извлечь все `#class:` теги и их определения
2. Извлечь все `#interface:` теги и их определения
3. Построить граф зависимостей между сущностями
4. Проверить согласованность определений
5. Найти противоречия в типах

**Проверки:**
- ResourceId везде определен одинаково?
- IResourceRepository везде имеет одинаковые методы?
- ResourceListItemDTO везде имеет одинаковые поля?
- Value Objects везде используют Result<T, E>?

**Команды:**
```bash
# Найти все определения ResourceId
grep -rn "#class:ResourceId" docs/ steps/

# Найти все определения IResourceRepository
grep -rn "#interface:IResourceRepository" docs/ steps/
```

**Выходной файл:** `.docs-meta/CONSISTENCY_ENTITIES.md`

---

### Этап 4: API контракты (1-2 часа)
**Источник истины:** `docs/contracts/api-contracts.md`

**Действия:**
1. Извлечь все `#api:` теги
2. Проверить что endpoints согласованы
3. Проверить что DTO соответствуют контрактам
4. Найти несоответствия

**Команды:**
```bash
# Найти все API endpoints
grep -rn "#api:" docs/ steps/
```

**Выходной файл:** `.docs-meta/CONSISTENCY_API.md`
